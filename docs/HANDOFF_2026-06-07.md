## Lib Mental Model

The Lib has moved to a mature explicit-surface model.

The author-facing declaration object is the module facade returned by
`lib.createModule(...)`. It declares capabilities before activation. Activation
builds a managed live module and publishes it into the Lib live-module registry.

After activation, author callbacks should use the scoped objects they receive:

- `host`: unphased safe module functions such as logging and miscellaneous support.
- `ui`: draw-time UI projection.
- `runtime`: runtime projection.
- `plan`: mutation/patch plan projection where relevant.

The important design shift: callbacks should be self-contained and receive their
needed context explicitly. Avoid module globals and old ambient host/store patterns.

### Data Lanes

Current conceptual lanes:

- `module.data` / `ui.data` / `runtime.data`
  - normal config storage
  - staged through UI
  - read by runtime
  - persisted/hashable depending on storage definition
- `module.status` / `runtime.status` / `ui.status`
  - runtime-published status
  - UI-readable
  - not normal config data
  - replaces public `runtimeOwned` language
- `module.actions` / `ui.actions`
  - UI intent after draw/commit
  - command-like, not a broad data lane
- `module.controls` / `ui.controls` / `runtime.controls`
  - module-defined composite config objects
  - controls compile private config storage and optional control-local actions
  - controls do not own status/runtime-owned storage
- `module.shared` / `ui.shared` / `runtime.shared`
  - shared data/events
  - shared publication writes are immediate publication writes, not staged config writes
- `module.cache`
  - current-run/current-lifecycle module-local cache; keep it for lifecycle-linked
    runtime state, not for UI/runtime bridging now handled by status.

### Controls

Controls are the key new module ergonomics tool.

They are best understood as small module-owned classes spanning UI and runtime:

- a template defines storage shape, UI methods, runtime methods, and optional
  internal actions
- an instance supplies the concrete data/meta
- Lib lowers the control into private `_...` aliases and exposes typed refs

Controls are not just custom widgets. Their value is that they span the UI/runtime
line while hiding storage plumbing and control-name details.

Design boundaries to preserve:

- Controls declare config storage only.
- Status and actions remain module-level coordination lanes.
- If many control templates start passing action refs through ad hoc `opts`, that
  is the pressure signal for a future first-class "control consumes action" binding.
- Nested controls were not needed for the current module ports and should not be
  introduced casually.

### Status And Future Task Direction

`runtimeOwned` was intentionally narrowed and renamed out of public `data` into
`status`.

There was discussion about a future "task/status+intent" concept that could bundle
UI intent and runtime-published state. The current conclusion was:

- keep `actions` command-like for now
- keep `status` as runtime-published state
- do not introduce tasks until a second or third real workflow beyond recording-like
  status appears
- if tasks are introduced later, state should probably be mandatory and intent optional,
  otherwise tasks and actions overlap too much

Do not rework actions/status now without a concrete module pressure case.

### Hashing

Hash groups were removed/retired as an author-facing compression mechanism. They
were too maintenance-heavy and fragile.

Current direction:

- keep deterministic hash serialization
- tables remain flexible live tables during runtime
- tables are flattened/snapshotted at hash boundaries when needed
- packed ints and bounded ints remain useful storage primitives
- if hashes become too long, prefer generic string compression as a future layer
  before reintroducing semantic hash-group layout

### Lifecycle And Commit

The draw lifecycle is now a first-class concept and should remain centralized.

The high-level shape:

1. UI draw stages config and triggers actions.
2. Staged config commits through the managed module.
3. Mutation/patch lifecycle updates only after successful config commit.
4. Status/runtime side effects are separated from config persistence.
5. Shared publish and post-commit work run through the lifecycle hooks rather than
   ad hoc draw-time writes.

The exact implementation lives in Lib docs/code; do not duplicate lifecycle order
in module docs unless linking to the canonical lifecycle doc.

## Module State

### GodPool

GodPool was cleaned into a simple, readable shape.

Current preferred module style:

- `data` is a real object/domain.
- logic files attach behavior directly through named functions rather than returning
  fake objects.
- UI attach is a side-effect-oriented function rather than a "ui object" pretending
  to own state.
- `main.lua` should be a composition root and not manually wire every small
  capability if a domain file can own the attach.

GodPool is the small-module reference for this style.

### BiomeControl

BiomeControl went through the largest data/control/UI redesign.

Current shape:

- biome data files declare their control instances close to their biome definitions
- the biome catalog is a hierarchical game-domain tree, not a broad public catalog
- data exposes/resolves game-domain concepts to control names or control metadata
- UI should ask the resolver for the relevant room/NPC/special control rather than
  hardcoding raw control names
- layout remains UI responsibility

Controls in play include:

- mode-like controls
- mode-with-range controls
- god-choice style controls
- dream-route style control

Recent cleanup themes:

- `base_storage` was eliminated as control templates absorbed remaining storage.
- transient tab UI state became file-local where appropriate instead of storage.
- dropdown/radio widgets gained lightweight visibility-table support for fixed data
  with mutable visibility booleans.
- room/miniboss labels and dropdown alignment were fixed.
- disabled F/G trial behavior should mean the trial/devotion encounter is disabled,
  not necessarily the base room itself.

BiomeControl still benefits from honest boring logic. Prefer explicit biome files
calling small helpers such as `patchForceOrDisableRoom(...)` over abstract
`applyEntry(...)` style loops that hide what a biome actually does.

### BoonBans

BoonBans is now the clearest proof of the controls model.

Current shape:

- `TraitSource` controls are the real catalog of boon/trait sources.
- Data hydrates definitions from game data and builds controls.
- A narrow source resolver translates game-domain info to control-domain info.
- `trait_info` is the logic-facing service that hides resolver/control plumbing.
- UI mostly uses control instances directly rather than catalog objects.

Key design result:

- The old broad catalog is gone as a general threaded object.
- Controls are the main data/UI/runtime abstraction.
- Source resolver is the one bridge helper from game data to control identity.

Important BoonBans concepts:

- `TraitSource` has multiple views: setup/force, checkbox list, rarity.
- display names are looked up locally in the UI/control layer when possible rather
  than being treated as persistent catalog data.
- Bridal Glow is a special UI/logic projection over multiple controls and lives
  separately.
- `trait_info` is intentionally the place logic asks questions like source/trait
  lookup, ban status, and rarity override.

Private padding:

- The old private-padding branches should not be merged directly.
- The feature was ported into the modern control-shaped BoonBans path.
- The intended release shape was to gate private padding through build/release
  configuration rather than carrying long-lived divergent branches.

Potential caution:

- Config crashes were fixed once by clearing the Chalk config folder. One underlying
  class of issue was controls reading/writing state directly instead of through a
  proper adapter layer. That was addressed by putting a stateful adapter boundary
  between controls and persistent/staged state.

## Design Principles That Emerged

### One Data Plane Until There Is A Real Domain Boundary

The old `cache` history matters:

- cache originally absorbed non-persistent/current-run concerns
- persistent cache became awkward because it wanted to be first-class storage
- runtime-write/UI-read eventually became `status`

Keep cache for lifecycle-domain state, not as a generic data bridge.

### Controls Are For Repetitive Leaf UI/Data Patterns

Guideline:

- simple module: widgets and direct ImGui are fine
- one big repeated surface: one control plus normal UI code is fine
- complex control-heavy module: compose UI out of controls

Controls are not layout. Layout belongs to the module UI.

### Data Should Stay Behind Resolvers

For complex modules, external logic/UI should not consume raw definitions or broad
catalogs unless they truly need the tree shape.

Preferred pattern:

- data owns definitions and game-data hydration
- data exposes controls and a narrow resolver
- logic asks domain questions through resolver/service helpers
- UI asks for control names/objects and lays them out

### Prefer Boring Explicit Files Over Smart Loops

The BiomeControl redesign showed that "generic catalog loop builds everything"
was harder to read than small files declaring concrete control instances.

Some repetition is a good price for being able to open one biome file and see what
it wires.

### Do Not Reopen Shared Infrastructure Without Pressure

Lib and Framework are in good shape. Future work should be module-driven. If a
module exposes a real pain point, then revisit Lib/Framework with that concrete
case.
